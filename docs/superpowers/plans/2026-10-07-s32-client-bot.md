# С32 — клиентский Telegram-канал Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (Native) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** /start, старые клиентские кнопки и уведомления работают через общий Mini App в одном Go-процессе.

**Architecture:** Существующий Runtime/transport расширяется клиентским каналом.
accounts проверяет текущую привязку, payments владеет legacy decoder/history,
notifications владеет outbox. Доменный результат и enqueue — одна транзакция.

**Tech Stack:** Go/stdlib, pgx/PostgreSQL, существующие River/Redis, React/TypeScript,
существующий Playwright. Новых зависимостей нет.

**Spec:** `docs/superpowers/specs/2026-10-07-s32-client-bot-design.md`

## Global Constraints

- Native inline; один fresh Astra/high whole-branch review и один авторский Critical/Important fix pass.
- origin/v2 → feature/s32-client-bot → PR/v2; Conventional Commits и Co-Authored-By.
- Только owned local fixtures, TLS 3X-UI 3.7.0; живой Happ запрещён.
- Старый operator outbox/hash, wt1, payment non-ack, UUID/source/IDs неизменны.
- /start не создаёт аккаунт до согласия; источник передаётся через signed start_param.
- Клиентский send ограничен 10 секундами, lease 60 секунд, recipient проверен под guard/account lock.
- Никаких чужих SQL/private imports, нового facade, реальных денег или публичного webhook.
- Token file-only; текст/URL без секрета, email, тела обращения и VPN-ключа.

## Review Focus

- Команда во время операторского пересмотра должна отменить диалог, а не стать причиной.
- Username/main-app сменились: startup сверяет getMe с token ID и не строит чужой deep link.
- Snapshot старой pay-кнопки имеет price=0 и не идентифицирует единственную оплату.
- Связь аккаунта меняется между claim и send: нельзя отправить старому получателю.
- После потерянного send-ответа возможен повтор уведомления, но деньги/выдача не повторяются.
