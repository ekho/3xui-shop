# С01: Web Trial Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** В тестовой среде клиент без Telegram регистрируется, запрашивает триал, получает доступ после решения оператора в существующем боте и подключается к VPN.

**Architecture:** Go backend владеет новыми web-аккаунтами, заявками и выдачей в выделенной 3X-UI; PostgreSQL хранит состояние и задания River. Python-бот доставляет карточки и передаёт решения через закрытый API. React-кабинет работает с публичным API того же backend.

**Tech Stack:** Go + Echo, PostgreSQL + pgx/sqlc, River, Redis для ограничителей; React + TypeScript + Vite; существующие aiogram/aiohttp и unittest. SQL-миграции Goose; Go testing/httptest и Playwright для проверок.

**Spec:** [Принятая спецификация С01](../specs/2026-10-01-s01-web-trial-design.md).

Дата: 2026-10-01. Статус: исполнение начато по команде пользователя «Продолжай», метод Native.
Базовый revision: `74c124906462f5b75a323aa9b80944dd08df2037`, `3xui-shop` 1.31.0.
План реализует только С01 из [роадмапа](../../roadmaps/2026-10-01-platform-roadmap.md).

## Global Constraints

- Название продукта не используется в именах модулей, команд, cookie, API и документов. Публичный HTTPS-origin кабинета задаётся настройкой `CABINET_ORIGIN`, а не фиксируется в коде.
- Только новые web-аккаунты: `account_id` UUID; `tg_id`/`legacy_user_id` nullable. SQLite старого бота не получает эти аккаунты. Импорт и привязка — последующие сценарии.
- Один backend владеет каждой новой заявкой/операцией. Бот не обращается к PostgreSQL и панели этой группы; backend не получает bot token.
- Апрув относится только к триалу. Отказ не блокирует регистрацию/вход, не вызывает `ApprovalService.apply_decision` и не меняет Stars/покупки.
- Только выделенная тестовая 3X-UI, одна настроенная панель, regular-инбаунды. Общая production-панель, импорт legacy и production-запуск в этот план не входят.
- Пароль задаётся после доказательства владения email: 15–128 Unicode code points, без trim/усечения; Argon2id ≥19 MiB/2 прохода/parallelism 1.
- Email token: 256 случайных бит/24 часа; код: 8 цифр/10 минут/5 попыток. Resend отзывает старые секреты.
- Cookie `__Host-session`: Secure/HttpOnly/SameSite=Lax/Path=/, без Domain; idle 7 дней, absolute 30 дней. В DB только hash ID, CSRF и точный Origin для изменений.
- Письма ≤1/мин и ≤5/час/email; login ≤5 неуспехов/15 мин/email и ≤30/15 мин/IP. Потеря Redis закрывает login/отправку писем с 503, но не текущие сессии и выдачу.
- Комментарий клиента ≤1000 символов; причина пересмотра 1–1000. Повтор после reject начинает только поддержка; использованный/зарезервированный триал не освобождается из-за ошибки HTTP.
- Approve + TrialGrant + Operation + River job — одна PG-транзакция; постоянные ключи и цели не меняются при повторе.
- Выдача: 5 попыток, backoff 10/30/120/300 сек; после неопределённой записи сначала сверка, затем needs_review при неизвестном результате.
- Панель: `totalGB` в байтах, положительный `limitIp=N+1`, zero unlimited; кабинет показывает N. Срок от первого начала выдачи, а не от каждого retry.
- Telegram claim: limit=1, lease=60 сек, send timeout=10 сек. Все решения проверяют реальный actor и allowlist в адаптере и backend.
- ru/en, подписи форм, клавиатура/focus, mobile/desktop, loading/error/empty. Опрос ожидающего статуса раз в 5 сек без перекрывающихся запросов; после конечного результата остановить.
- VPN-ссылка только владельцу после проверенной выдачи, `Cache-Control: no-store`; нет ссылки, паролей или открытых токенов в логах/аудите/карточках/email.
- React-admin, оплата, Mini App, полный чат поддержки, reset/change password, расширенные инструкции и бонусы не реализуются в С01.
- Исполнение разрешено командой пользователя «Продолжай». Работа ведётся в отдельном worktree; local commit разрешён, push/PR/release/production deploy не выполняются.

## Review Focus

1. **RF1 — письмо устарело между enqueue и send:** после resend старый worker не отправляет действующий старый секрет; проверка в задаче 1.
2. **RF2 — Unicode и границы времени:** пароль не усечён по байтам/UTF-16, сессия не продлевается за absolute expiry; проверки в задачах 1/2/6.
3. **RF3 — решение записано, HTTP-ответ потерян:** повтор/конкурентная кнопка показывает победившее решение и не создаёт вторую выдачу; проверки в задачах 3/5.
4. **RF4 — send успел, lease/result истекли:** повторная карточка безопасна, поздний/чужой result не меняет доставку; проверки в задаче 5.
5. **RF5 — backup старше фактической записи панели:** после restore сверка завершает исходную Operation с прежним сроком/ключами; проверки в задачах 4/8.

Для внешних границ использовать реальный `*http.Client`/httptest и конкретные pgx/River/Redis; часы — `func() time.Time` в Service для детерминированных проверок.

Go: `1.27.1` ([официальные загрузки](https://go.dev/dl/)); Echo: `github.com/labstack/echo/v5`, который требует Go ≥1.25 ([quickstart](https://echo.labstack.com/guide/quickstart/)). Node ≥22.12 согласно [Vite](https://vite.dev/guide/). При начале задачи 1/6 выбрать совместимые опубликованные patch-версии зависимостей и закрепить их в go.mod/go.sum/package-lock; tool versions — в go.mod tool directives. CI/сборки не используют `@latest`.

OpenAPI `3.0.3` в `docs/api/openapi.yaml`: новый контракт без существующих потребителей. Это конкретизация предварительного OpenAPI 3.1 в общем архитектурном черновике; семантика принятой С01 сохраняется. `oapi-codegen` генерирует только Go models ([официальный пример](https://github.com/oapi-codegen/oapi-codegen#generating-api-models)); Echo routes остаются обычными обработчиками. `openapi-typescript` генерирует frontend types ([CLI](https://openapi-ts.dev/cli)); никаких handwritten копий DTO.

В `components/schemas` определить именованные `RegisterInput`, `RegistrationAccepted`, `VerifyInput`, `VerifyResult`, `ResendInput`, `ResendAccepted`, `LoginInput`, `LoginResult`, `Account`, `AccountResult`, `TrialRequestInput`, `TrialRequest`, `CurrentTrialRequest`, `Subscription`, `SubscriptionKey`, `ClaimInput`, `ClaimResult`, `TelegramJob`, `TelegramResultInput`, `DecisionInput`, `DecisionResult`, `ReconsiderInput`, `ReconcileInput`, `ReconcileResult`, `APIError`. UUID — `uuid.UUID` в Go через generator/sqlc override, строки в JSON/TS. Денежных типов здесь нет.

HTTP-хендлер каждой операции: `func (a *API) <OperationIdWithCapital>(c *echo.Context) error`. `func New(svc *s01.Service, cfg s01.Config) *echo.Echo` в `httpapi/api.go` подключает только уже реализованные routes. `NewService(pool *pgxpool.Pool, limiter *redis.Client, queue *river.Client[pgx.Tx], cfg Config) *Service` и `type Config struct` объявляет задача 1; Service хранит конкретные зависимости и `now func() time.Time`. Каждая следующая задача добавляет свои методы/поля без изменения прежних сигнатур.

`Config.CabinetOrigin string` читается из `CABINET_ORIGIN` и задаёт Origin allowlist, ссылки подтверждения email и публичный адрес кабинета. Значение — HTTPS-origin без path/query/fragment; не выводить его из клиентского Host header. Изменение домена или названия не требует переименовывать модули, cookie или API.

Задача 1 объявляет `s01.Error{Status int; Code, Message string; Details map[string]any}` с `Error() string` для HTTP-mapping. Details допускает только winning request state у авторизованного internal decision409. SQL/transport errors преобразуются в безопасный SERVICE_UNAVAILABLE503; логировать correlation ID/code, без request body, headers credentials и исходного error string. Strict decode ограничивает JSON body16KiB; превышение даёт INVALID_INPUT400.

River args только с ID: `MailArgs{DeliveryID uuid.UUID}` и `ProvisionArgs{OperationID uuid.UUID}`. Работники: `MailWorker.Work(context.Context, *river.Job[MailArgs]) error` и `ProvisionWorker.Work(context.Context, *river.Job[ProvisionArgs]) error`. Service получает insert-only River client; отдельный worker client в том же backend-процессе исполняет уже реализованные очереди. Поэтому задача 3 сохраняет provision job до появления worker в задаче 4, без фиктивного исполнителя. Секретный почтовый payload хранится зашифрованным в минимальной `mail_deliveries`; удаляется после send/отзыва, а не остаётся в истории River jobs. Ключ шифрования вне DB/backup. Постановка через `InsertTx` в том же pgx transaction ([River](https://riverqueue.com/docs/transactional-enqueueing)); миграции River выполняются штатным `rivermigrate` отдельно от прикладных ([документация](https://riverqueue.com/docs/migrations)).

`testkit.Open(t *testing.T) *Env` создаёт отдельную тестовую DB и Redis namespace; `Env` содержит `Pool *pgxpool.Pool`, `Redis *redis.Client`, `Now time.Time`, `Advance(time.Duration)` и `Close()`. Credentials читает из `S01_TEST_DATABASE_URL_FILE`/`S01_TEST_REDIS_URL_FILE`. Неверная/неподготовленная среда — ошибка prerequisite до запуска тестов; обязательные CI-тесты не превращать в skip.

Для любой задачи: сначала выполнить указанный red check с минимальным компилируемым stub, затем green. FAIL из-за отсутствия Docker/Go/секретов не подтверждает red. Локальный commit после green допустим только в отдельно разрешённом исполнении; selective staging, чужую `.omo/` не включать. Не выполнять push/PR/release/production deploy.
