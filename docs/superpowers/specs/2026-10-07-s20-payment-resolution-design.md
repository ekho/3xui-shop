# С20 — Разбор оплаты и подтверждённый возврат

Версия `2026-10-07-s20-v1`; владелец — `payments`, задача [#27](https://github.com/ekho/3xui-shop/issues/27). Основа — `2026-10-05-modular-monolith-v1`, С18 и С19. Реализация и слияние в `v2` разрешены автономно; внешняя приёмка остаётся отдельной.

## Сценарий

Оператор открывает любой сохранённый заказ или конкретное поступление из истории клиента. Карточка показывает серверный снимок тарифа, исходные деньги, состояние выдачи, незавершённую проверку и записанный возврат. Несуществующий или чужой заказ/поступление даёт 404. Чтение не вызывает платёжный сервис или панель.

Для ручного перевода сохраняются существующие одобрение/отказ с суммой и причиной. PAID без доступа восстанавливается операцией С19; существующая операция доступа восстанавливается через С07/С08/С19. Оператор видит эти пути и не может повторно оплатить или создать вторую выдачу из карточки.

Если деньги уже полностью возвращены внешним способом, оператор записывает подтверждение: конкретное поступление, идентификатор внешней операции, причину и явное подтверждение полного возврата и сохранения текущего доступа. Это учёт подтверждённого оператором факта, а не отправка нового перевода. Для YooMoney, ручного перевода и YooKassa сумма — исходный gross в RUB, без возможности её подменить. Для Cryptomus/Heleket оператор вводит фактическое положительное количество исходного криптоактива, не больше сохранённого `payment_amount`; актив берётся из исходного `payer_currency`. Он подтверждает, что возврат полный с учётом внешних комиссий. USD-цена заказа, неизвестный USD-net и количество криптовалюты остаются разными фактами; курс не вычисляется.

Источник новой записи всегда `operator`, а не доказательство провайдера. Внешний идентификатор — неприватный идентификатор операции (ASCII буквы/цифры, точка, дефис, подчёркивание, 1–128 символов); реквизиты, ссылки с токенами и произвольный provider JSON не принимаются. Сохраняется один полный возврат на поступление и один внешний идентификатор на платёжный метод. Частичные возвраты и автоматическая отправка выплат не добавляются в С20: в прежнем внешнем обработчике их нет. Native Stars-refund принадлежит С34/С35. Существующие платёжные настройки не получают прав на выплаты.

Защищённое, незачисленное, нулевое или неизвестной валюты поступление нельзя объявить возвращённым. Позднее/неподходящее по сумме поступление можно вернуть в исходном размере, сохранив его старые признаки проверки. Не требуется активный способ оплаты: подтверждение старых фактов доступно после отключения новых продаж.

## Деньги и доступ

`purchase_refunds` — добавляемый журнал. Исходные заказ, quote/hash, payment status/paid_at, gross/net, provider proof, funding receipt, access ID и замороженный target не переписываются. UPDATE/DELETE журнала запрещены; откат миграции с записями запрещён. Аудит хранит оператора, клиента и причину; его ID совпадает с ID возврата, который связывает заказ и поступление. Старое поле audit `operation_id` остаётся пространством trial_operations.

Перед записью возврата payments получает существующий account-access lock и в одной транзакции повторно проверяет роль оператора, принадлежность, поступление, уникальность и идемпотентность. Активный исполнитель выдачи даёт 409 `ACCOUNT_ACCESS_BUSY`; запись без проверки не делается.

Возврат funding-поступления запрещает все будущие вызовы выдачи через общую проверку денег. Если его операция доступа ещё не applied, публичная операция `vpn.RetirePurchaseAccessTx` переводит только эту операцию в `skipped`, снимает lease, сохраняет target, фактические шаги, reset/write flags и provenance. Это отмена дальнейших попыток, без утверждения, что ранее выполненные частичные изменения панели откатились. Applied остаётся applied. Возврат другого поступления не отменяет законную выдачу funding-поступления. Бот не становится вторым владельцем денег или доступа.

Текущий доступ, срок, профиль и лимиты не меняются при возврате. Если нужно ограничить или компенсировать доступ, оператор отдельно использует существующие операции С07/С08 с текущим состоянием и причиной. Дни не вычитаются автоматически.

Финансовая проверка закрыта, только когда у заказа есть поступления и каждое имеет полный подтверждённый возврат. Старые причины проверки остаются в истории. Такой невыданный заказ больше не блокирует новую покупку; существующий applied-тариф по-прежнему проверяется общей политикой С16/С17. Новое отдельное позднее поступление вновь оставляет открытую финансовую проверку. Дубликат старого callback не открывает повторную выплату или выдачу.

## API и совместимость

Авторский источник — `docs/api/openapi.yaml` (JSON, OpenAPI 3.0.3), API `/api/v1`, версия `1.0.0`. Изменения добавляемые; старые методы, поля, статусы, body hashes и сохранённые replay остаются совместимыми. Генерация — `make generate` в backend и `npm run api:generate` в web.

- POST `/api/v1/operator/clients/{id}/orders/{order_id}/payment-case`, `getOperatorPaymentCase`: необязательный `receipt_operation_id`; 200 `PaymentCase`. Без указанного поступления выбирается funding, иначе последнее поступление. Возвращаются `order`, nullable `receipt`/`refund`, `financial_review_open`, `can_confirm_refund`.
- POST `/api/v1/operator/clients/{id}/orders/{order_id}/refunds`, `confirmPurchaseRefund`: `receipt_operation_id`, `reference`, `reason`, `confirm_full`, `keep_access`; для криптовалюты также `returned_amount`. 201 `PaymentRefund`, UUID Idempotency-Key обязателен. Одинаковый ключ/тело возвращает ту же запись; другой ввод с ключом — 409 `IDEMPOTENCY_CONFLICT`; другое подтверждение того же поступления/внешней операции — 409 `PAYMENT_REFUND_CONFLICT`.
- История С18 получает `kind=refunds` и необязательный массив `refunds`; старые обязательные массивы остаются. Курсор `(created_at,id)` и размер 50 сохраняются. Клиент видит только свои возвраты; оператор — выбранного клиента.
- `PurchaseOrder` получает необязательный `fully_refunded`; старые потребители могут его игнорировать. История исходного PAID не превращается в CANCELED.

Оба новых operator POST требуют действующей подтверждённой web-сессии, роли, Origin и CSRF; запросы строго проверяются по схеме, неизвестные поля отвергаются. Ответы private/no-store. Ошибки 400/401/403/404/409/429/503 используют существующий envelope. Идентификаторы и суммы остаются строками/UUID, денежные значения не проходят через float. Отсутствуют новые процессы, очереди, библиотеки и права на provider payouts.

## Интерфейс

История заказов/поступлений оператора получает кнопку открытия конкретной карточки. Выбор привязан к клиенту, заказу и поступлению; смена владельца или потеря прав скрывает старые данные, отменяет запросы и очищает согласие. У повторной отправки неизменного ввода тот же ключ; изменённый ввод получает новый ключ. После успешного подтверждения обновляются карточка и история.

В карточке есть исходные факты, существующие ручные решения/восстановление, форма фиксации полного возврата и пояснение о сохранении доступа. Клиент читает возвраты в истории. RU/EN, подписи, клавиатура, focus, screen reader, загрузка/ошибка/пустое состояние и узкий экран проверяются.

## Приёмка

1. Настоящие HTTP + PostgreSQL/Redis: чтение старого выбранного заказа, права/Origin/CSRF/владение/строгие поля; full-refund всех пяти внешних методов с точными величинами, неизвестным net и защитой от подмены криптоактива.
2. Повторы одного/разных ключей, общий внешний идентификатор, одновременная выдача/возврат, позднее дополнительное поступление; одна запись/audit, никакой второй выдачи. Неизменность исходного proof/hash/status/target и UPDATE/DELETE/Down guards.
3. Browser: форма оператора и история клиента RU/EN, смена клиента при позднем ответе, отзыв роли, повтор после timeout, клавиатура и mobile.
4. Собственный Docker-стенд с настоящей 3X-UI **3.7.0** и заглушкой YooMoney: после возврата прекращается незавершённая выдача; существующие client UUID/expiry/лимиты/traffic сохраняются после двух рестартов. Ни живой Happ, ни production не затрагиваются.
5. Focused → общий suite/generated/static → один свежий final-review → максимум один исправительный проход → PR в v2, проверка точного SHA/релиза/образов и закрытие #27. Проверки провайдеров, фактического перевода и внешнего HTTPS не считаются выполненными локальным fixture.
