## Цель и выбор

Оператор отправляет сообщение одному зарегистрированному клиенту или всем, предварительно проверяет содержание и адресатов, видит результат по каналам, изменяет/удаляет свою последнюю отправку. Клиент закрывает сообщение. Сценарий переносит существующие Python notification/list/card/ID flows в Go и кабинет; старый Python runtime удаляет С47 после полного покрытия и импорта.

Выбран собственный небольшой NoticeService внутри notifications с нынешними client/mail outbox. Система только из сообщений бота не покрывает клиента без Telegram; новая универсальная очередь/сервис рассылок добавляет второй lifecycle без необходимости. Один Go-процесс, нынешние PostgreSQL/River/Echo/React-admin, установленный x/net/html; новых зависимостей и процессов нет. Письма auth/security и автоматические напоминания С27 сохраняют свои правила.

## Операторский путь

1. Раздел «Уведомления» React-admin: «Клиент»/«Все». Персональный адресат — account UUID из существующего поиска по ID/Telegram ID/списка или ссылки карточки. Номер Telegram не является account UUID; произвольный chat/email не принимается. Оператор задаёт текст и комментарий операции1..512 Unicode codepoints.
2. Preview сохраняет неизменяемые HTML/plain text, mode, reason, audience и первые credential/channel proofs. Показывает content, общее число адресатов и доступность каждого канала на момент preview, предупреждение о независимом email consent и ограничениях отзыва. Новый preview того же автора делает неподтверждённый старый недействительным; срок15мин по DB-clock. Неизвестный personal UUID →404; пустая аудитория →409. В preview нет сетевой отправки.
3. Отдельная кнопка подтверждения отправляет только `{confirmed:true}` и preview UUID. Подтверждение фиксирует notice/revision/recipients/channel actions/audit/jobs в одной Tx. Role и own last revision проверяются повторно. Ответ, потерянный после commit, повторно читается по тому же preview без второй операции. Истёкший/заменённый preview, чужой автор, false/лишние поля или устаревший expected_revision отклоняются. Уже подтверждённый own preview остаётся доступен для idempotent replay после15мин: возвращаются факты именно этой операции с актуальными outcome, текущая revision не откатывается; UI отдельно обновляет last.
4. Результат показывает actual текущие счётчики каждого канала и «Обновить результат». Добавленная после preview регистрация не попадает в рассылку. Изменившиеся eligibility/credential/binding/consent не переадресовывают копию новым email/TG; канал пропускается. Cabinet visibility сохраняется для того же account UUID после штатной смены пароля, при текущем допуске к кабинету.
5. «Изменить»/«Удалить» доступны только для собственной последней подтверждённой отправки. Новый отдельный preview фиксирует notice UUID, expected_revision, тех же адресатов и новое содержание/reason; подтверждение увеличивает revision. Редактирование не добавляет адресатов и не открывает закрытые клиентом записи. Удалённое notice повторно изменять нельзя. Другая новая отправка делает подготовленное изменение старой отправки конфликтным.

## Каналы и пределы

| Канал | Отправить | Изменить | Удалить / закрыть |
| --- | --- | --- | --- |
| Кабинет / Mini App | Собственная запись текущего допущенного аккаунта | Текущий body/revision; закрытое не возвращается | Withdraw / собственный dismiss |
| Telegram | Копия frozen current binding, cabinet button | editMessageText для записанного успешного message ID; не начатую первоначальную копию заменяет актуальная send | Реальный deleteMessage для записанного outgoing private message младше48ч; own close проверяет binding/actor/bot/keyboard/message |
| Email | Plain text и cabinet URL, только отдельный explicit notice opt-in | Уже доставленное письмо неизменно; старое не начатое отменяется, новое не создаётся | Не начатое отменяется; доставленное и начатое отозвать нельзя |

Начатую сетевую операцию нельзя гарантированно отозвать. Потерянный send ACK без message ID не позволяет безопасно изменить/удалить неизвестное сообщение или заменить его второй send. При SMTP ACK/commit loss обычное письмо может повториться. Telegram <48ч относится к удалению outgoing private сообщений; это не общее ограничение редактирования обычных сообщений бота. Нормативные ответы и ограничения — [официальный Bot API](https://core.telegram.org/bots/api#deletemessage), [editMessageText](https://core.telegram.org/bots/api#editmessagetext).

Каждая operation/recipient/channel имеет собственные pending/succeeded/failed/skipped/unknown/unchanged facts. succeeded означает ACK соответствующей операции; failed означает известный отказ, а не доказательство отсутствия предыдущего эффекта. unknown означает отсутствие надёжного подтверждения; UI не заменяет его «доставлено» или «удалено». unchanged отражает канал без новой операции, например уже отправленное письмо. 429 использует существующий retry_after; новые notice Telegram jobs ограничены5 сетевыми попытками, после неизвестного результата сохраняется unknown. Старые delivery policies не меняются.

В текущем кабинетном компоненте —20 записей на страницу, предыдущая/следующая, loading/error/retry/empty, дата и отдельный accessible Close. Собственная notice email preference defaultfalse, опция доступна при подтверждённом независимом email/password; opt-out доступен всегда. Она не использует reminder preferences и не отменяет security mail. Dismiss скрывает запись и прекращает не начатые новые копии; Telegram-кнопка `on1:<deliveryUUID>` дополнительно пытается удалить её действительное сообщение и честно сообщает об отказе. Прежний `cn1` остаётся прежним cosmetic close.

## Форматирование и границы ввода

Текст1..4096 Unicode codepoints до разбора + существующий16384-byte JSON cap. UTF-8/NUL/контрольные символы кроме LF/TAB отклоняются, пустой видимый текст недопустим; ничего не усекать. x/net/html tokenizer нормализует безопасный набор: b/strong, i/em, u/ins, s/strike/del, tg-spoiler/span class=tg-spoiler, code/pre (code class=language-* только внутри pre), blockquote expandable, a с HTTPS либо exact tg://user?id=positiveDecimal, tg-emoji с числовым emoji-id и Unicode fallback. Неправильное nesting, неизвестные элементы/атрибуты, event/style/script, опасные/credential URL и неподдержанные entities отклоняются. Telegram получает одинаковый с preview normalized HTML; web строит React nodes из этого allowlist без произвольного innerHTML, custom emoji отображает Unicode fallback. SMTP — полученный plain text со ссылками. Source HTML тела хранится только приватно в notifications.

## Владельцы, данные и API

NoticeService consumes typed same-Tx ports: accounts AudienceTx и NoticeRecipientTx (малый wrapper доставленного ReminderRecipientTx, различает отсутствующий UUID и сбой), RequireOperator, LockOperatorTx и WithNoticeDelivery. Accounts владеет sorted actor/target locks, fresh role/source/credential/binding proofs. Telegram transport не читает SQL notifications; HTTP не читает чужие таблицы. SMTP использует тот же conn/mail guard; SQL row locks освобождаются до сети. Lock order accounts pair → notifications current/action/outbox; confirm не блокирует все аккаунты аудитории. Контроль роли непосредственно перед dispatch не обещает отзыв уже начатого внешнего запроса.

Новая миграция00032: `notices` (owner, current preview/revision, deleted), `notice_previews` (immutable body/reason/snapshot/expected revision, expiry/confirmation), `notice_recipients` (stable notice/account proof, closed/visibility), `notice_actions` (immutable operation/recipient references и отдельные channel outcomes), `notice_preferences`. Preview audience — приватный typed JSON snapshot account IDs/credential/locale/TG/email hash/consent; payload не возвращается API. Последующие действия сохраняют первый recipient proof. Индексы unique notice/account и action preview/recipient обеспечивают отсутствие двойной операции. Append собственные nullable action/prior-delivery refs в client outbox и action ref для kind=operator_notice в mail; старые строки/ClientOutcome JSON/result hashes/зашифрованные payload bytes сохраняются. Down отказывается удалять retained facts; возврат к старому binary после появления нового kind запрещён, нужен совместимый binary или восстановление согласованного backup.

Public operation types: NoticePreviewInput(mode send/edit/delete, audience personal/all, account_id optional только personal/send, body только send/edit, expected_revision только edit/delete, reason); NoticePreview(id, notice_id, mode, revision, html, text, reason, expires_at, recipient_count, cabinet_count, telegram_count, email_count); NoticeBatchResult(version, notice nullable, revision, latest action, channel counts); NoticeResult(version, email_enabled, email_available, page, per_page20, total, notices[id,revision,html,text,created_at]). IDs — canonical nonzero UUID; revision/page bounded int32; unknown discriminator/result fails closed в UI. Результаты без private recipient identities.

Additive runtime `operator-notices-v1`, шесть путей:

- GET `/api/v1/notices?page=1` →NoticeResult; POST `/api/v1/notices/preferences` `{email_enabled:boolean}` →NoticeResult; POST `/api/v1/notices/{id}/dismiss` empty body →204.
- POST `/api/v1/operator/notices/previews` →NoticePreview201; POST `/api/v1/operator/notices/previews/{id}/confirm` `{confirmed:true}` →NoticeBatchResult200; GET `/api/v1/operator/notices/last` →NoticeBatchResult200.

Contracts сначала в docs/api/openapi.yaml, затем существующие Go/TS generators и server/UI. Own methods сохраняют web cookie+CSRF либо signed source-bound Mini bearer, exact allowlist; operator методы только текущий verified web operator+CSRF. Existing16384-byte limit, timeout, exact origin/no-cache/error wrappers действуют. Strict schema отвергает actor/chat/email/revision/body override на confirm. Старые99 paths/167 schemas/3security и allowed DTO enums не меняются.

Audit в той же Tx: action notice_sent/notice_edited/notice_deleted, actor и reason, AccountID=personal target либо actor для all; audit.ID=preview.ID для связи с notification snapshot. operation_id не используется (trial namespace). Audit metadata/export/logs не содержат body/email/TG/VPN material. Dismiss/preference сохраняют own metadata events. С29 строит историю/retention, С46 импортирует IDs/состояния, С47 выполняет единственный writer cutover; их scope/status не закрываются С28.
