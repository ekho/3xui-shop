# С39 — распределение и обслуживание клиентов в пуле

Версия: `2026-10-09-s39-server-pool-v1`. Владелец: #41 / `vpn`.
Основание: принятый роадмап, модульный монолит v1 и разрешение самостоятельно
готовить документы, выполнять Native и сливать последовательные PR в `v2`.
Это решения реализации в пределах данного разрешения, а не новое подтверждение пользователя.

## Результат и граница

Один Go-процесс обслуживает несколько 3X-UI **3.7.0**. При первой выдаче backend
выбирает доступный сервер; все дальнейшие операции и ссылки используют назначение
аккаунта. Кабинет, Mini App и Telegram используют прежние операции модулей.
С38 добавляет интерфейс инфраструктуры с более узкими правами нынешнего IsDev.
С40 завершает сверку, С46 — импорт, С47 — переключение и удаление Python.
Здесь не добавляются выбор сервера клиентом, автоматический перенос или редактор серверов.
Production, реальные платежи, внешний SMTP и переключение живого Happ исключены.

## Исходные факты и выбранный подход

Python `ServerPoolService` синхронизирует доступные подключения и считает всех
назначенных пользователей, включая неактивных. Выбор: минимум клиентов среди
серверов ниже `max_clients`; если таких нет — минимум среди всех доступных.
Отсутствие доступных серверов не означает смену назначения существующего клиента.
Готовый `subURI` имеет приоритет; иначе используются домен, порт и путь подписки.
Go пока использует одну панель и общую базовую ссылку.

Я сохраняю VPN owner, `PanelClient`, River, блокировку доступа аккаунта и неизменяемые
targets. Реестр и резервации хранятся в PostgreSQL. Подключение создаётся для конкретной
операции и закрывается ей: отдельный кэш, сервис, фоновый процесс и зависимость не нужны.
Sync вызывается при выборе для первой выдачи и через ядро управления С38.
Вариант списка серверов только в env не покрывает управление без перезапуска;
отдельный сервис пула увеличивает число владельцев одной панельной операции.

## Данные и совместимость

- `vpn_servers`: стабильный текстовый ID, уникальное имя и HTTPS host, мягкая ёмкость,
  сохранённая базовая ссылка подписки, online/время наблюдения, revision и retired.
  Username/password/token/CA остаются общей file-only конфигурацией, как в старом боте.
- `vpn_server_reservations`: одна резервация на аккаунт, сервер и ровно одна собственная
  trial/access operation. Резервация и её операция фиксируются в одной транзакции.
  Она не выставляет `had_subscription` и не подтверждает применение grant.
- `accounts` предоставляет публичное чтение загрузки назначений в caller Tx.
  SQL чужого модуля и private imports не используются.
- Настроенные `PANEL_ID`, `PANEL_URL`, `SUBSCRIPTION_BASE_URL` дают прежний первый
  сервер, лениво добавляемый без перезаписи существующего реестра. Для него прежний
  deployment не задавал ёмкость: NULL означает отсутствие ограничения. Для явно
  зарегистрированного сервера сохраняется заданное целое `max_clients >= 0`;
  ноль означает отсутствие свободных мест, но допускает общий fallback полного пула.
- ID и host не переиспользуются для другой панели; удаление сохраняет tombstone.
  Изменённый host настроенного первого сервера не подменяет уже сохранённую панель.
  Старые операции с заполненным `panel_id` и targets исполняются по прежнему ID.
  UUID, `panel_key`, `sub_id`, деньги, provenance, ответы idempotency и audit сохраняются.
  Down миграции блокируется при сохранённых фактах нового реестра/резерваций.

## Выбор и конкурентные первые выдачи

Sync выполняет ограниченные TLS/auth/read запросы вне SQL транзакции. Неуспешная
панель отмечается недоступной; ошибка одного сервера не завершает HTTP/jobs/Telegram.
Наблюдение записывается только при прежней revision и если более новое наблюдение
его ещё не заменило. Старый запрос не возвращает в online удалённый сервер.

Под короткой общей transaction lock пула выбор считает `assigned + reserved`.
Сначала рассматриваются доступные серверы со свободным местом, затем полный пул;
сортировка — по загрузке и стабильному ID. Provider calls под этой SQL lock запрещены.
Уже сохранённая резервация сохраняет выбор при повторе и рестарте.

Новая одобренная trial operation сначала имеет пустой `panel_id`. До lease, начала
trial period и первого provider write worker выбирает сервер и атомарно сохраняет
`panel_id` с резервацией. Если весь пул offline, River snooze сохраняет одобрение,
reserved grant и операцию; период и попытки панельной записи ещё не начинаются.
Исторический непустой `panel_id` никогда не выбирается заново.

Первичная покупка и операторская выдача используют доступный сервер для подготовки
без резервации неоплаченного checkout. Перед сохранением нового access target тот
же выбор подтверждается под lock пула вместе с резервацией и операцией. Если загрузка
изменила выбор, подготовка повторяется: оплаченный заказ остаётся в очереди, оператор
получает прежний безопасный conflict. До этого provider writes отсутствуют.
Весь offline до checkout даёт безопасную unavailable; уже оплаченный заказ не теряется.
Отмена/ошибка до сохранения операции не оставляет резервацию. No-client metadata intent
не резервирует ёмкость. Применение назначения и освобождение резервации происходят в одной Tx.
Неопределённая запись сохраняет свой сервер и recovery evidence; blind create retry
по-прежнему запрещён без подтверждённого duplicate guard версии панели.

## Назначенные клиенты и потребители

Assigned ID разрешается только через его запись, независимо от последнего online
наблюдения. Offline, retired или неизвестный ID не заменяется первым сервером.
Provider read/write может завершиться unavailable или needs_review по прежним правилам;
readback identity, funding/source/actor guards, lease и immutable target сохраняются.

Охват: trial/provision; payment checkout и paid fulfillment; renewal/change-plan;
операторские compensation/plan/profile/ban/reset; trial/access profile и чтение;
месячный reset; subscription key и карточка клиента; statistics и reminders.
Числа пользователей/резерваций принадлежат backend; число клиентов панели учитывается
отдельно. Statistics возвращает состояние каждого сервера и unknown для неподтверждённых
клиентов. Reminders используют snapshot назначенного сервера; outage одного не лишает
здоровые серверы собственных подтверждённых фактов. Неподдерживаемый bulk read 3.7.0
не объявляется успешным и не превращается в неточное число.

## Базовые ссылки и границы входных данных

Существующая явная HTTPS base не переписывается. Отсутствующая заполняется через
read-only `POST /panel/api/setting/all` 3.7.0: `subURI`, иначе `subDomain` или host
панели, `subPort` и `subPath`; схема следует настройке TLS подписки. Невалидные
настройки или выключенная подписка не заполняют пустую base. IPv6 получает корректные
скобки и порт; стандартный порт может быть опущен. Хвост всегда нормализуется до `/`.
URI с userinfo/query/fragment, неверный порт/путь и plaintext не выдаются кабинету.
Ссылка содержит `sub_id` именно назначенного аккаунта; URL/секреты не пишутся в logs.
Ошибка discovery не удаляет прежнюю проверенную base.

Публичный HTTP API v1 не требует нового выбора или поля клиента. Новые операции
реестра являются доверенными module ports; внешний адаптер С38 обязан сначала
проверить инфраструктурную роль и записать audit. Обычный клиент не управляет host.

## Приёмка и доставка

1. Два TLS сервера: первая выдача на выбранный сервер, параллельные резервации,
   мягкая заполненность, весь offline без записи и без расхода trial period.
2. Повтор и рестарт сохраняют operation/assignment/keys. Outage назначенного,
   неизвестный ID и stale sync не вызывают запись в другую панель.
3. Все перечисленные операции работают на втором сервере с прежними role/source,
   funding, idempotency, profile, ban и месячными правилами; отмена не оставляет резерв.
4. Subscription discovery проверяет приоритет, disabled/ошибки, IPv6, границы URI
   и неизменность явной ссылки; карточка показывает реальное назначение.
5. Statistics/reminders разделяют серверы, данные и unknown; не меняют деньги/grants/keys.
6. Ранний вертикальный trial slice предшествует расширению остальных consumers.
   Затем fresh compiled one-process и локальные Docker панели 3.7.0/TLS SMTP.
   Все owned fixtures, никаких изменений живого Happ/Telegram или доверия macOS.
7. Generated/static/connected suites, один свежий Astra/high whole-branch review,
   один авторский проход; PR в v2, успешный required source CI, guarded manual merge,
   проверенный annotated prerelease и amd64/arm64 образы.

Текущий Platform CI достиг лимита 35 минут на дублирующем push С37, при успешном
полном PR CI той же версии. Для полного охвата пула его budget повышается до 60 минут;
состав проверок сохраняется. Внешняя приёмка YooMoney остаётся отдельной pending проверкой.
