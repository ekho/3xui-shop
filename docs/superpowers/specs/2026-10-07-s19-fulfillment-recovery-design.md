# С19 — Восстановление незавершённой выдачи

Задача [#26](https://github.com/ekho/3xui-shop/issues/26), контракт `2026-10-07-s19-fulfillment-recovery-v1`. Основание: С19 роадмапа `afaeacf652964453ddd61883aa6da6a0d285783c` и модульный монолит v1, owner #55. Спецификация, план, локальная реализация и merge разрешены владельцем автономно; выбран Native.

## Результат и границы

Система продолжает оплаченную выдачу после временного сбоя или перезапуска. Если результат физической записи неизвестен, оператор проверяет и повторно запускает **ту же** сохранённую операцию. Повтор webhook, запроса или worker не создаёт дополнительный оплаченный период, VPN-клиента или денежное подтверждение одной и той же провайдерской операции.

Используем уже доставленные payments/subscriptions/VPN operations и River. С19 исправляет операторский путь безопасной проверки, защищает его от устаревших ответов и добавляет доказательство восстановления оплаченной операции после остановки скомпилированного Go-процесса. Новая очередь, второй планировщик, migration, API/DTO, финансовый writer и refund не нужны. Разбор спорных денег и возвратов принадлежит С20; Stars — С34/С35; обслуживание — С42. Их факты оплаты и сохранённые задания должны совместимо использовать этот контракт.

## Неизменяемые условия

- Один Go-процесс HTTP/River/Telegram, один go.mod; public module operations, без чужих SQL/private пакетов.
- База `5246923c6a7fe92a1f29693d401fde292368d63d` от origin/v2; feature/s19-fulfillment-recovery, без codex/, PR в v2.
- Существующие quote, financial proof, order/funding/access IDs, абсолютный target, API/DTO/hash и migrations 15–22 сохраняются.
- Checkout действует 30 минут. Просроченный pending не означает canceled; время фактической оплаты отличается от времени доставки уведомления.
- Причина операторского действия: 1–1000 Unicode code points после trim, без NUL. Актуальные права, Origin/CSRF, UUID Idempotency-Key, audit сохраняются.
- Название/домен только в конфигурации; ru/en, keyboard/screen reader и 375px.
- Собственные localhost данные/заглушки. Реальные деньги, публичный callback, production, живой Happ/VPN, Mac trust, внешние SMTP/Telegram не входят.

## Сценарии и сохранённые данные

| Условие | Поведение |
| --- | --- |
| Повтор одного достоверного provider operation | Тот же receipt/funding/order; повторная выдача не создаётся. Другой реальный перевод сохраняется отдельно, даже если деньги относятся к тому же заказу. |
| Подтверждённые деньги, target ещё не создан | PurchaseArgs содержит order_id. Worker заново проверяет funding, аккаунт и политику, затем атомарно сохраняет один access ID и абсолютный target вместе с заданием. |
| Перезапуск после commit денег/задания или access target | River продолжает сохранённое задание. После появления target новое время не добавляется, quote/identity/target не пересчитываются. |
| Панель выполнила создание/изменение, ответ потерян | Worker читает реальную панель и сравнивает identity/expiry/лимиты/membership с target. Подтверждённое совпадение позволяет закончить ту же операцию; неизвестный/частичный результат требует needs_review. |
| reset начат, ответ потерян | Без нового согласия повтор только проверяет counters. Ноль подтверждает результат; ненулевой/недоступный результат остаётся needs_review. Новый reset допустим только при явном согласии, которое расходуется перед записью. |
| Истёкший pending и новое оформление | Старый заказ перестаёт предлагать оплату/мешать новому checkout. Его денежная история и возможность достоверного позднего уведомления сохраняются. |
| Уведомление задержалось, реальная оплата была до expiry | Достоверная оплата может финансировать прежний заказ при остальных действующих guards. |
| Реальные деньги после expiry/cancel, несовпадение, protected или спорный receipt | Факт денег сохраняется, blind issuance запрещена; review остаётся видимым. Retry выдачи не превращает спорные деньги в достоверное funding. |

Владельцы остаются прежними: payments хранит заказ, quote, подтверждение и результат выдачи; subscriptions даёт операторские public operations; VPN хранит target/steps/reset flags и выполняет физические writes. На аккаунт действует существующий owner lock; SQL Tx не удерживается на сетевом запросе. Успешное применение access и отметка результата funded order остаются атомарными.

## Операторский интерфейс

До access ID оператор повторяет подготовку оплаченного заказа через `ReconcilePurchaseOrder(ctx, actor, target, id, key, PurchaseReconcileInput{Reason})`. Для существующего access ID используется `ReconcileAccessOperation(ctx, actor, target, id, key, AccessReconcileInput{Reason, AcknowledgeResetCost})`. HTTP paths, поля и ответы не меняются.

Для неоднозначного reset подтверждение по умолчанию отправляет `acknowledge_reset_cost=false`: это проверка результата без нового сброса. Текст объясняет оба исхода: нулевой counter позволит завершить выдачу, иной/неизвестный counter оставит операцию на разборе. Отдельный unchecked checkbox разрешает повторный сброс с потерей нового трафика; только тогда отправляется true. Кнопка подтверждения доступна и без checkbox.

Согласие привязано к конкретному подтверждению и операции. Cancel, новая форма подтверждения, другая операция или обновлённое состояние очищают согласие. После сетевой ошибки сохранённый неизменённый запрос можно повторить с тем же key; изменённая операция/reason/consent получает новый key. Клиент не повторяет write автоматически.

Уход с карточки/смена клиента отменяет request и запрещает его позднему ответу обновлять другую карточку или передавать ей старый access ID. Аналогично чтение старого состояния не перезаписывает результат принятого write. Busy blocks повторные submit; 401/403 передаются существующему parent denial flow. На сервере актуальная роль проверяется при приёме операторского действия. Уже законно поставленная оплаченная выдача продолжает работать после отзыва роли оператора: её право определяется подтверждёнными деньгами, а не будущей ролью инициатора.
