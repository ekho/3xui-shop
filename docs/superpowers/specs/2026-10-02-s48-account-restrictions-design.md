# С48 — ограничения аккаунта вместо одобрения регистрации

Статус: подготовлено к согласованию; реализация ещё не начата.
Основание: запрос «Реализуй С48, затем С09, затем С07/С08» и
[роадмап](../../roadmaps/2026-10-01-platform-roadmap.md).
Исходная ревизия: `32b020573bdca9a59d67ab65b250dc113b20388b`.

## Результат и границы

Новый клиент регистрируется без решения оператора. Подтверждение email
остаётся обязательным для web-входа; заявка на бесплатный триал остаётся
отдельным процессом С01/С06. Отказ в триале не ограничивает аккаунт.

Оператор в React-admin явно ограничивает аккаунт или снимает ограничение
с обязательной причиной. История старых pending/rejected/approved сохраняется,
но больше не является очередью обязательного одобрения регистрации.
Снятие ограничения — явный эквивалент старого «вернуть отклонённого»;
предыдущее решение не стирается и новая заявка на регистрацию не создаётся.

С48 не меняет подписку, VPN-ban, ограничения переписки, Stars-рекуррент,
платежи или идентификаторы подключения. Платёжные последствия ограничений
рассматриваются с денежными сценариями С20/С35, а не выполняются скрыто здесь.
Полный импорт пользователей и переключение старого бота относятся к С46/С47.
С48 предоставляет необходимую часть схемы/контракта и проверяемую репетицию
переноса истории; реальная production SQLite не читается и не изменяется.

## Что уже есть

- `accounts.restricted` уже проверяется при входе, authenticated API,
  выдаче ключа, работе оператора и заявках на триал.
- `accounts.vpn_banned` и support-ban — отдельные состояния.
- С06 предоставляет web actor UUID, роль оператора, блокировки account/role,
  историю audit и карточку клиента; новые роли и новая система аудита не нужны.
- Старые `users.approval_status`, `approval_requested_at`,
  `approval_decided_at`, `approval_decided_by` и записи `audit_log`
  существуют в SQLite. Старый отказ мог отменять Stars; этот side effect
  не переносится в независимое ограничение аккаунта.

## Модель и перенос истории

В PostgreSQL добавляется read-only снимок старой регистрации, привязанный к
account UUID: source legacy_user_id/tg_id, status, requested_at, decided_at,
decided_by. Сохраняются NULL неизвестных дат и операторов. Pending не получает
выдуманного решения; отказ в регистрации не выдаётся за отказ в триале.
Решения из `audit_log` сохраняются отдельными неизменяемыми историческими
записями с исходными ID, временем, актором и источником. Импорт не печатает
персональные поля или содержимое payload; UI показывает только относящиеся
к одобрению метаданные, не произвольный payload.

Исходные действия — ровно `approval.approve` и `approval.reject` из
`AuditAction`; остальные события остаются в неизменённой SQLite для С29/С46.
Историческая запись сохраняет source audit ID, target tg_id, created_at,
action, actor_type/id/name и source. Nullable поля сохраняются nullable;
из отсутствующего actor нельзя создавать web-оператора. Payload не относится
к контракту этой выборки и не передаётся клиентскому кабинету.

Отображение при первом переносе:

| Исходное состояние | История | Эффективное ограничение |
| --- | --- | --- |
| approved | Сохраняется | Текущее restricted сохраняется |
| pending | Сохраняется, без обязательного approval | Текущее restricted сохраняется |
| rejected | Сохраняется как прежний отказ | restricted=true до явного снятия оператором |

Импорт идемпотентен по source ID. Повтор идентичной записи — no-op; изменённый
снимок с тем же ID, несовпадение account/tg_id/legacy_user_id или отсутствующий
account — ошибка и откат всего пакета. Нельзя молча пропускать пользователей,
создавать фиктивный email или выдавать новые UUID/sub_id/server. Первая миграция
rejected может только установить restricted, никогда массово его снять.
После явного снятия повторный импорт того же снимка не включает ограничение
заново. Snapshot и изменение ограничения фиксируются одной транзакцией.
Import применяет такой же protected-operator guard: rejected для аккаунта
с действующей operator role отклоняет пакет, а не закрывает операторский вход.
Существующие ограниченные аккаунты остаются ограниченными независимо от
статуса импортируемой регистрации.

Контролируемый перенос — административная CLI-процедура, не публичный HTTP
endpoint. SQLite читается в read-only режиме стандартным Python sqlite3;
структурированные данные передаются импортирующей Go-команде через stdin,
без промежуточного dump с персональными данными. Dry-run проверяет весь пакет
без записи; отчёт содержит только счётчики и стабильные коды ошибок.
Общий identity-import С46 должен завершиться до этой процедуры; локальная
репетиция создаёт согласованные тестовые identities и проверяет эту границу.

CLI-контракт: `server import-legacy-approvals --dry-run` либо `--apply`,
строго типизированный JSON-пакет на stdin и existing DATABASE_URL_FILE.
Пакет содержит version1, массив users с исходными approval полями и массив
approval_events с перечисленными метаданными. Экспортёр
`deploy/s48/export_legacy_approval.py` принимает путь к контролируемому снимку,
открывает SQLite `mode=ro` и отправляет пакет только в stdout для pipe.
Неизвестные поля/версии/статусы, повтор source ID внутри пакета, некорректные
даты или нецелые идентификаторы отклоняются до применения. Исходная timezone
для legacy naive timestamps задаётся явно, не берётся из локального Mac.
Dry-run не вызывает panel API, не создаёт jobs и не отзывает sessions/proofs.
Apply использует те же guards и один commit для snapshots/events/restrictions;
ошибка на последней записи откатывает первые. Отчёт — users/events/changed
counts и error code, без source IDs/имён/email/тел токенов или raw SQL errors.

## Операторская операция

POST `/api/v1/operator/clients/{id}/restriction`:
`{restricted: boolean, reason: string}` и `Idempotency-Key` UUID.
Ответ — эффективное состояние, время изменения и web actor UUID.
Actor берётся только из сессии. JSON до16 KiB, unknown fields запрещены,
reason после trim от1 до1000 Unicode-символов, без NUL, origin/CSRF обязательны.
Существующие OpenAPI operations и DTO не меняются; новые поля карточки
истории добавляются совместимо и описываются до изменения server/consumer.

В одной транзакции: существующий `lockOperatorPair`, повторная проверка роли,
проверка идемпотентности, изменение restricted и append-only audit.
Повтор того же ключа/тела возвращает исходный результат без второго события;
другой body с тем же ключом —409. Изменение роли во время запроса не обходится.
Самоограничение web-оператора запрещено; операции над аккаунтом с активной
operator role запрещены, пока роль не отозвана существующей CLI-процедурой.
Это сохраняет доступ оператора и не добавляет вторую систему управления ролями.

При переходе в restricted все сессии аккаунта отзываются, активные credential
proofs отзываются и ciphertext соответствующих писем очищается существующими
С02 queries. Это делается атомарно с состоянием и аудитом. Снятие ограничения
не восстанавливает старые сессии или коды: клиент заново входит.
Неизменившееся состояние с новым ключом возвращается без нового state-change
аудита; история миграции сохраняется. Ошибка/rollback не оставляет частичную
блокировку, потерянный аудит или отозванные сессии без изменения состояния.

403 `ACCOUNT_RESTRICTED` остаётся понятным состоянием клиента с безопасным
выходом и указанием обратиться в поддержку. Прямой API-запрос не открывает
кабинет/ключ. Публичное восстановление пароля сохраняет нейтральный ответ;
оно не снимает ограничение. Уже выданный VPN-доступ остаётся прежним.

## React-admin и старый бот

В карточке клиента: независимые account restriction, VPN-ban, support-ban;
форма причины и действие «Ограничить аккаунт»/«Снять ограничение».
Перед ограничением показывается подтверждение последствий; во время POST
поля блокируются, при ошибке текст/ключ повторной попытки сохраняются.
Успех обновляет состояние и историю; показываемый секрет подключения
очищается. RU/EN,375px, keyboard focus, семантические labels/errors обязательны.

Историческое approval показывается отдельным блоком с исходными датами
и актором, без кнопок одобрения регистрации. Исторические pending/rejected
не скрываются из поиска, не удаляются и не смешиваются с триалами.
Первая карточка содержит максимум50 событий старой регистрации и флаг
`legacy_has_more`; дальнейшее чтение использует existing защищённый history
endpoint с новым kind `legacy` и стабильным cursor source time/source ID.
Исходные неизвестные даты отображаются «неизвестно», не датой импорта.

Backend не запускает registration approval reminders. В контуре, переведённом
на backend, старый scheduler/middleware/кнопки регистрации отключаются вместе
при cutover; карточки апрува триала С01 продолжают работать. Для оставленного
legacy-контура обработчики и данные сохраняются до С32/С46/С47, чтобы С48
не переключал живой бот раньше согласованного окна обслуживания. Runbook
явно проверяет единственного владельца обработки и отсутствие registration
reminders после переключения; наличие кода legacy не считается его запуском.

## Приёмка

1. Новый web-аккаунт после email-подтверждения входит без approval; отказ в
   триале не ограничивает аккаунт. Новая регистрация не создаёт reminder job.
2. Ограничение с причиной и настоящим web actor закрывает login/API/key,
   отзывает старые sessions/proofs; снятие требует нового входа. Подписка,
   traffic, VPN-ban/support-ban и identities до/после совпадают.
3. Неоператор, чужая/отозванная сессия, forged actor, CSRF/Origin bypass,
   пустая/длинная/NUL-причина и protected operator target отклоняются без записи.
4. Конкурирующие restrict/unrestrict, повтор/lost response и конфликт body
   проверены: согласованный итог, один аудит на реальный переход, полный rollback.
5. Локальный dry-run/import/reimport сохраняет pending/rejected/approved,
   NULL-метаданные и исходные audit actors/IDs; конфликт/неизвестный account
   откатывает пакет. restricted не снимается массово, явное снятие не отменяется
   повторным импортом, SQLite-снимок остаётся byte-identical.
6. React-admin показывает старую историю отдельно, выполняет оба действия,
   корректно переживает pending/error/retry; RU/EN/mobile/keyboard проверены.
7. Backup/restore сохраняет restriction, snapshot и историю; auth-material
   после restore обрабатывается существующей процедурой С02/С06.
8. Прежние С01–С06 и API consumers не сломаны; локальный runbook фиксирует
   границу будущего cutover/reminders. Production, real-data import, Happ,
   Mac VPN/trust/clipboard и внешняя публикация не входят в эту приёмку.

После согласования: план С48, реализация и локальная приёмка; затем С09,
затем С07/С08 в принятом порядке.
